HomeMediaViewer — 局域网流媒体分享与点播 方案分析与价值评估

目标：实现一个 Android 应用，让同一局域网内的多台 Android 设备互相发现、浏览、点播彼此终端上的音视频文件，无需拷贝源文件。 后续将扩展 iOS / 鸿蒙。

1. 产品定位与核心场景

一句话：让同一局域网内的多台 Android 设备，互相发现、浏览、点播各自终端上的音视频文件，无需拷贝源文件。

三项核心能力： 1. 内嵌轻量流媒体服务 — 每个设备既是「分享端(服务端)」，也是「点播端(客户端)」 2. 设备发现与会话管理 — 局域网内自动发现其他设备及媒体清单 3. 远程流式点播 — 边下边播，源文件不出设备

2. 总体架构（P2P + 无中心）

┌───────────┐        媒体/控制流        ┌───────────┐
│ 设备A      │ ◄──────────────────────► │ 设备B      │
│ 服务端+客户端│                            │ 服务端+客户端│
└───────────┘                            └───────────┘
      ▲    ◄── 每个设备同等地位 ──►    ▲
      └──────────────┬────────────────┘
                     对等网络(无中心服务器)

无中心服务器，设备间直接连接。可选一个「发现协调」角色（mDNS/DNS-SD 组播）只做设备发现，不承载媒体流。

3. 技术栈与关键选型

层次 技术选型 说明
语言 Kotlin Android 官方推荐
流媒体服务 NanoHTTPD 或自写 SocketServer 轻量内嵌 HTTP 服务
媒体列表/控制 HTTP REST API + JSON 设备能力、媒体目录
点播传输 HTTP Range 请求（字节范围） 支持拖动播放、轻量
播放器 ExoPlayer / Media3 支持 HTTP 播放、缓存
设备发现 mDNS/DNS-SD（Network Service Discovery / JmDNS）+ UDP 组播兜底 自动发现
序列化 JSON（Gson/Moshi） 设备与媒体描述
持久化 SQLite / Room 设备与媒体缓存
权限 存储权限 + 局域网权限(Android 13+ Nearby)

关键选型理由： - HTTP + Range（而非 RTSP/自定义协议）：ExoPlayer 原生支持 HTTP，Range 天然支持拖动，无需额外流服务器，开发量最小。 - mDNS 为主 + UDP 组播兜底：mDNS 是标准零配置发现；网络禁用组播时用 UDP 探测。 - ExoPlayer/Media3（不用 IjkPlayer）：本质是标准 HTTP 播放，IjkPlayer 的 ffmpeg 解码优势在此不必要，Media3 更现代、维护好。

4. 核心功能设计

4.1 内嵌流媒体服务（分享端）

  • 每台设备启动时绑定局域网 IP + 端口（默认如 :8080）
  • 接口：
  • GET /media → JSON 媒体列表
  • GET /media/{id} → 流媒体（支持 Range）
  • GET /thumb/{id} → 缩略图（可选）
  • 用 Content-Range: bytes 0- 响应支持拖动。

4.2 设备发现模块

  • 启动时广播自己的服务和媒体
  • 监听 UDP/组播，维护在线设备表
  • 周期心跳，探测设备离线

4.3 点播传输模块

  • 点播端拿到目标设备 IP:Port + 媒体 id
  • 构造 http://ip:port/media/{id} 交给播放器
  • 播放器 Range 请求，ExoPlayer 自动缓冲、拖动

4.4 媒体库扫描

  • 扫描本机媒体目录（Music/Movies/Downloads + 自定义）
  • 提取元数据：标题、时长、分辨率、缩略图
  • 形成可分享清单

5. 通信协议设计

设备描述

{
  "deviceName": "Xiaomi-12",
  "deviceId": "uuid",
  "ip": "192.168.1.5",
  "port": 8080,
  "mediaCount": 12,
  "categories": ["video", "audio", "image"]
}

媒体描述

{
  "id": "uuid",
  "title": "电影.mp4",
  "type": "video",
  "duration": 7200,
  "size": 523,
  "url": "http://192.168.1.5:8080/media/uuid",
  "thumbUrl": "http://192.168.1.5:8080/thumb/uuid"
}

关键：URL 即点播凭证 — 媒体 URL 由 ip:port/media/id 构成，点播即请求该 URL，无共享源文件传输。

6. UI 与交互流程

主界面（媒体浏览）： - 顶部：在线设备列表 - 主体：当前选中设备的媒体网格/列表，带类型筛选

播放界面： - 点击任意设备条目 → 打开播放器（ExoPlayer）→ 直接在线缓冲播放 - 进度条拖动基于 Range

交互：下拉刷新设备、Tab 切本地/设备媒体

7. 后续扩展性设计

  • 跨平台（iOS/Win/鸿蒙）：服务端协议固定为 HTTP+Range；客户端换播放器（iOS AVPlayer 原生支持 HTTP；鸿蒙 MediaKit 同样适用；发现层换 DNS 报文）。
  • 加能力：转码（ffmpeg）、断点续传、播放鉴权（token）、多用户并发控制。

9. 价值分析

9.1 业务/用户价值

  • 去中心化：不依赖互联网/云，断网也能局域网共享
  • 零拷贝：点播不复制源文件，节省设备存储
  • 即时：无需上传云端，本地直接分享
  • 隐私安全：数据在局域网内不出域，比云盘更私密

9.2 技术价值

  • 通用性：HTTP+Range 标准化协议，天然便于跨平台移植
  • 低依赖：核心依赖标准库 + 官方播放器，维护成本低
  • 可演进：从 P2P 流媒体可扩展 WEB 播控、CDN 推送、临时分享码

9.3 商业 / 生态价值

  • 适用于智能家居（电视/手机间共享）、办公（会议资料分发）、演示（多屏素材共享）
  • 可作为「设备间媒体共享」底座，后续接入 DLNA/Chromecast 透传

10. ffmpeg 介入边界分析

10.1 核心链路不涉及 ffmpeg

环节 使用的技术 ffmpeg
媒体服务端 自写 HTTP + Range 字节流 ❌ 纯文件流式读取
传输 HTTP 协议 ❌
播放 ExoPlayer/Media3（MediaCodec 硬解） ❌
设备发现 mDNS/UDP ❌

为什么不用 ffmpeg：Media3 已内置支持几十种常见格式（H.264/H.265/AAC/MP3/MP4/MKV 等），走 Android 系统硬解，零额外集成成本，对「局域网设备间分享自录视频」场景足够。

10.2 可能需要 ffmpeg 的可选场景

场景 使用方式 二开程度
播放冷门格式（AV1/私有封装） Media3 的 FFmpegDecoder 扩展 低
服务端转码（目标端打不开） 内嵌 ffmpeg 库/CLI 中
抽帧做缩略图 调用抽帧 低
多码率自适应(HLS) ffmpeg 转 HLS 切片 中

10.3 ffmpeg 介入结论

  • 三条核心需求（内嵌服务、设备发现、远程点播）均不需要 ffmpeg 二次开发。
  • 只在「冷门格式兜底」「转码」「抽缩略图」时以低度集成方式介入，且可后置。
  • 鸿蒙端系统解码器覆盖面弱于 Android，届时更值得引入 ffmpeg（后话）。

11. 流媒体服务端性能分析

11.1 服务端角色澄清

服务端本质是「持源文件 + 响应 HTTP 流读文件」，瓶颈是磁盘 IO + 网络带宽，不是 ffmpeg 能加速的。ffmpeg 是解码/转码的 CPU 密集库，不参与「把文件交给网络」这条路径。

11.2 各维度对比

性能维度 ffmpeg 是否更好 说明
传输吞吐/延迟 ❌ 无帮助 同 read()+write() 流式 IO，瓶颈在 IO/网络
秒开/拖动/Seek ❌ 反而更差 Range 直接填播放器缓冲最快，转码拖慢起播
高并发多设备 ❌ 负担 转码是 CPU 密集，并发骤降；IO 型服务并发更高
冷门格式兜底 ✅ 库集成 终端解码扩展，非服务端二开
实时转码 ✅ 但牺牲性能 仅当目标设备解码不了才做

11.3 性能结论（核心）

流媒体服务端不用 ffmpeg 性能反而更好——它对此场景的 IO/网络性能无提升，还会拖慢起播和并发，是纯 CPU 负担。ffmpeg 的正确位置是「终端解码兜底扩展」，不是「服务端」。

真正的性能瓶颈在服务端 IO 设计（零拷贝/sendfile、多线程 accept）和播放器缓冲策略。

12. 风险与权衡

风险 缓解
IP 地址变化导致断开 每次用设备发现查最新 IP，或走 mDNS 服务名
大文件传输内存压力 流式读(Range 分片)，不整文件入内存
跨子网/防火墙 限定同一网段，可配置手动添加 IP
编解码不兼容 用 ExoPlayer(几十种格式)兜底，预留转码
安全性 加访问鉴权(token Query 或注入)

13. 总体结论

  • 技术成熟、落地快：HTTP+Range 服务端 + mDNS 发现 + ExoPlayer 播放 是一条低风险、高通用的实现路径，直接满足三条需求。
  • 不涉及 ffmpeg 二次开发，ffmpeg 仅在可选场景以低度集成介入，且可后置。
  • 首轮迭代建议 M1→M4 打通最简闭环，再逐步打磨。
